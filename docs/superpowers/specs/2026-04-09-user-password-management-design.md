# 用户级密码管理设计

## 概要

当前系统仅支持注册、登录和通过数据库脚本直接修改密码，缺少面向业务用户的密码管理能力。当管理员需要协助用户处理无法登录问题时，只能通过数据库手工重置密码；普通用户也无法在系统内自助修改自己的登录密码。

本设计采用页面职责拆分方案：

- 为管理员新增独立的用户管理页，用于查看用户列表并为指定用户重置密码
- 为登录用户新增独立的账户页，用于查看自己的账户信息并修改自己的密码

本方案复用现有 `users.password_hash` 存储结构，不引入新表或 schema 变更，重点补足系统内的密码管理闭环。

## 背景与现状

当前实现涉及以下模块：

- `backend/routes/auth.py`：注册、登录、当前用户信息
- `backend/services/auth_service.py`：密码哈希、登录校验
- `frontend/src/views/LoginView.vue`：登录页面
- `frontend/src/views/RegisterView.vue`：注册页面
- `frontend/src/views/AdminSettingsView.vue`：当前仅包含 AI 设置

现状特点：

- 普通用户没有“修改密码”入口
- 管理员没有“用户管理 / 重置密码”入口
- 密码哈希逻辑已统一封装在 `auth_service.py` 中，使用 `pbkdf2:sha256`
- 当前用户身份由 JWT 维护，后端已有管理员权限判断模式

现有问题：

- 用户遗忘密码或密码错误时，管理员只能通过数据库人工处理
- 普通用户无法自助修改密码，增加运维支持成本
- 用户管理与个人账户缺少独立页面，职责边界不清晰

## 目标

### 功能目标

1. 管理员可查看系统用户列表
2. 管理员可为任意指定用户直接重置密码
3. 登录用户可查看自己的账户信息
4. 登录用户可输入旧密码后修改自己的密码
5. 修改后的新密码可立即用于登录，旧密码失效

### 设计目标

1. 将“管理别人”和“管理自己”拆分到两个页面，职责清晰
2. 保持密码哈希逻辑统一，不在路由层散落实现
3. 不修改数据库结构，降低上线风险
4. 保持与现有 JWT 鉴权和管理员校验模式一致

## 非目标

本次设计不包含以下范围：

- 忘记密码 / 邮箱找回密码流程
- 手机验证码、短信找回
- 用户禁用、删除、角色管理
- 邮箱修改、用户名修改
- 密码强度评分、复杂密码策略面板
- 修改密码后强制踢出所有在线会话

## 信息架构与页面划分

### 1. 用户管理页

新增独立管理员页面：

- 路由建议：`/admin/users`

页面职责：

- 查看用户列表
- 搜索/定位目标用户（首版可选，不强制）
- 为指定用户重置密码

该页面仅管理员可访问，用于“管理别人”。

### 2. 账户页

新增登录用户账户页面：

- 路由建议：`/account`

页面职责：

- 查看当前用户基本信息
- 修改自己的密码（输入旧密码 + 新密码）

该页面对所有登录用户开放，用于“管理自己”。

### 3. 页面职责边界

#### 用户管理页

- 仅管理员可访问
- 面向管理对象用户
- 提供用户列表和管理员重置密码能力

#### 账户页

- 任意登录用户可访问
- 面向当前登录用户本人
- 提供账户信息展示和自助修改密码能力

## 后端接口设计

### 1. 管理员接口

#### `GET /api/admin/users`

用途：返回用户管理页的用户列表数据。

权限：

- 仅管理员可访问

返回字段建议：

- `id`
- `username`
- `email`
- `is_admin`
- `created_at`

返回示例：

```json
[
  {
    "id": 1,
    "username": "nianyu",
    "email": "admin@local.test",
    "is_admin": true,
    "created_at": "2026-04-01T23:24:06.899855"
  }
]
```

#### `PUT /api/admin/users/<int:user_id>/password`

用途：管理员为指定用户设置新密码。

权限：

- 仅管理员可访问

请求体：

```json
{
  "new_password": "new-password-123"
}
```

处理规则：

- 校验目标用户存在
- 校验 `new_password` 非空
- 校验新密码长度至少 6 位
- 使用统一密码哈希逻辑更新 `password_hash`
- 不需要旧密码

成功响应：

```json
{
  "message": "密码已重置"
}
```

### 2. 当前用户账户接口

#### `GET /api/account`

用途：返回当前登录用户的账户信息。

权限：

- 仅登录用户可访问

返回字段建议：

- `id`
- `username`
- `email`
- `is_admin`
- `created_at`

说明：

- 如果实现上倾向复用现有 `GET /api/auth/me`，则账户页也可以直接复用该接口，不强制新增
- 但从语义上，单独提供 `/api/account` 更利于后续扩展账户能力

#### `PUT /api/account/password`

用途：当前用户修改自己的密码。

权限：

- 仅登录用户可访问

请求体：

```json
{
  "current_password": "old-password",
  "new_password": "new-password-123"
}
```

处理规则：

- 根据 JWT 获取当前用户
- 校验用户存在
- 校验 `current_password` 正确
- 校验 `new_password` 非空
- 校验新密码长度至少 6 位
- 更新 `password_hash`

成功响应：

```json
{
  "message": "密码修改成功"
}
```

失败场景：

- 用户不存在 / 登录失效
- 旧密码错误
- 新密码为空
- 新密码长度不足

### 3. 路由与服务层建议

建议新增：

- `backend/routes/admin_users.py`
- `backend/routes/account.py`

建议在 `backend/services/auth_service.py` 中补充：

- `set_user_password(user, new_password)`
- `change_password(user, current_password, new_password)`
- `validate_new_password(new_password)`

设计理由：

- 统一密码哈希逻辑
- 路由层只负责权限与参数接入
- 后续若增加密码规则，服务层可集中维护

## 前端页面与交互设计

### 1. 用户管理页

建议路由：`/admin/users`

页面结构：

- 用户列表区域
- 重置密码弹窗或内联表单

用户列表字段建议：

- 用户名
- 邮箱
- 管理员标识
- 创建时间
- 操作列（重置密码）

管理员点击“重置密码”后：

- 打开弹窗
- 展示目标用户名（只读）
- 输入新密码
- 输入确认密码
- 点击提交后调用管理员重置密码接口

交互细节：

- 列表加载中状态
- 空列表提示
- 提交 loading 状态
- 显示/隐藏密码按钮
- 成功后关闭弹窗并清空输入框
- 成功 toast：`密码已重置`

### 2. 账户页

建议路由：`/account`

页面结构：

- 账户信息区
- 修改密码区

账户信息区展示：

- 用户名
- 邮箱
- 是否管理员
- 注册时间

修改密码区字段：

- 当前密码
- 新密码
- 确认新密码
- 提交按钮

交互细节：

- 支持显示/隐藏密码
- 当前密码错误时给出明确提示
- 提交成功后清空密码表单
- 成功 toast：`密码修改成功`

### 3. 表单校验

#### 管理员重置密码

- 新密码不能为空
- 新密码长度至少 6 位
- 确认密码必须一致

#### 用户修改自己密码

- 当前密码不能为空
- 新密码不能为空
- 新密码长度至少 6 位
- 确认密码必须一致

### 4. 导航建议

管理员导航新增：

- 用户管理

登录用户导航新增：

- 账户设置 / 我的账户

说明：

- 用户管理入口仅管理员可见
- 账户页入口对所有登录用户可见

## 测试方案

### 后端测试

#### 管理员用户列表

验证：

- 管理员访问 `GET /api/admin/users` 成功
- 非管理员访问返回 403
- 未登录访问返回 401

#### 管理员重置密码

验证：

- 管理员可成功重置目标用户密码
- 新密码可登录
- 旧密码失效

- 新密码为空时返回 400
- 新密码长度不足时返回 400
- 非管理员访问返回 403

#### 用户自助修改密码

验证：

- 正确旧密码可修改成功
- 新密码可登录
- 旧密码失效
- 旧密码错误时返回 400 或 401
- 新密码为空时返回 400
- 新密码长度不足时返回 400

### 前端测试

#### 用户管理页

验证：

- 管理员可访问 `/admin/users`
- 普通用户不可访问
- 用户列表可展示
- 重置密码弹窗可打开与提交
- 密码不一致时阻止提交

#### 账户页

验证：

- 登录用户可访问 `/account`
- 账户信息可展示
- 修改密码成功后清空表单

### 联调验证

管理员链路：

1. 管理员登录
2. 进入用户管理页
3. 为某用户重置密码
4. 目标用户使用新密码登录成功
5. 旧密码登录失败

普通用户链路：

1. 普通用户登录
2. 进入账户页
3. 输入旧密码并修改为新密码
4. 退出并使用新密码重新登录成功

## 上线影响说明

### 数据库影响

本方案仅复用 `users.password_hash`：

- 不新增表
- 不修改字段
- 无需数据库迁移

### 后端影响

- 新增管理员用户管理接口
- 新增账户密码接口
- 不影响现有登录、注册与 AI 设置逻辑

### 前端影响

- 新增用户管理页
- 新增账户页
- 导航新增入口

### 兼容性影响

- 现有用户数据完全兼容
- 现有登录流程不变
- 新功能按需新增，不影响旧功能使用

## 风险与边界

### 管理员误操作风险

建议：

- 使用确认弹窗
- 显示目标用户名
- 提交成功后给出明确提示

### 修改密码后的会话处理

首版建议：

- 修改密码后不强制当前用户退出登录
- 后续若有更高安全要求，再补充“修改密码后使旧 token 失效”机制

### 权限控制风险

必须以后端权限判断为准，前端隐藏入口仅作为辅助交互，不作为安全边界。

## 预期收益

- 管理员可直接处理用户登录问题
- 用户可自助修改密码，减少人工支持成本
- 用户管理与个人账户职责清晰，便于后续扩展
